# Geography processing scripts

***IMPORTANT NOTE: This repo relies on loading data from the ONS Open Geography Portal. Changes to that service may break these scripts.***

This repository contains a number of scripts and source files for processing geographic data files for [Census maps](https://www.ons.gov.uk/census/maps), [Build a custom area profile](https://www.ons.gov.uk/visualisations/customprofiles/), [Explore local statistics](https://www.ons.gov.uk/explore-local-statistics/) and other products maintained by the ONS Data Visualisation team. The scripts also generate vector map tiles that are used across a number of other products.

The various outputs generated by these scripts is described in [the docs folder](docs/README.md).

## System requirements

The scripts in this repo have dependencies that will only run on a Mac or Linux system (including [Windows Subsystem for Linux](https://learn.microsoft.com/en-us/windows/wsl/install)). You will need to install the following dependencies in order to run the scripts:

- [NodeJS](https://nodejs.org/en) (version 22 or later)
- [GDAL](https://gdal.org/index.html) (included with [QGIS](https://qgis.org/))
- [Tippecanoe](https://github.com/felt/tippecanoe)

In addition, the scripts use commands including **zip**, **unzip**, **gzip** and **rm**, which should be available on virtually any MacOS or Linux-based system.

## Running the scripts

First install the NodeJS dependencies:

```bash
npm install
```

Each script is then run with `npm run {script-name}`. The work happens in three stages:

1. **Check the source files** (optional): `npm run check-sources` looks for new, changed or retired datasets on the Geoportal, so you can update `/config/source-files.js` first.
2. **Process the source files**: `npm run process-sources` downloads and archives the source files, then processes them into the boundaries, master lookup and best-fit lookups that the outputs are made from. These steps must run in order, and `process-sources` stops at the first one that fails.
3. **Make the outputs** you need: area lists, area metadata files, vector tiles, postcode lookups and search tiles. Most are large and slow to generate, so they're left out of `process-sources`. Each depends only on the processed source files, not on the others, so run whichever you need, in any order or in parallel.

Then see [Deploying to S3](docs/Deploying-to-S3.md) to publish the outputs.

| Stage | Command | What it does |
| ----- | ------- | ------------ |
| 1 | `npm run check-sources` | Optional. Reports new, changed or retired source datasets |
| 2 | `npm run process-sources` | Runs, in order: |
|   | ↳ `download-files` | Downloads the boundaries, centroids and lookups (from the archive or the Geoportal) |
|   | ↳ `archive-files` | Archives new or changed source files (needs write access; skipped with a warning otherwise) |
|   | ↳ `make-virtual-boundaries` | Makes the UK, Great Britain and England and Wales boundaries |
|   | ↳ `get-metadata` | Area names, areas, centroids and start/end years |
|   | ↳ `get-relations` | Parents and successors, written to the master lookup (`/input/lookups/lookup.csv`) |
|   | ↳ `get-best-fits` | Census 2021 best-fit lookups |
| 3 | `npm run make-lists` | Area lists (`/output/lists`) |
|   | `npm run make-geos` | Area metadata files (then `make-cm-geos` for Census Maps, and `check-centroids` to check them) |
|   | `npm run make-vtiles` | Vector tiles (then `zip-vtiles` to package them) |
|   | `npm run make-oa-vtiles-lookups`, then `make-oa-vtiles` | Output Area vector tiles |
|   | `npm run make-postcodes` | Postcode lookup files |
|   | `npm run make-search-tiles` | GeoJSON search tiles |

Each step of `process-sources` can also be run on its own (eg. `npm run get-best-fits`), as long as the steps before it have been run.

### Choosing which geographies to process

Many scripts accept `--geo` and `--year` options, so you can update one geography without commenting out parts of the config files. Options go after a `--`:

```bash
npm run download-files -- --geo wd --year 2026
npm run make-geos -- --geo ltla,wd
npm run make-vtiles -- --geo wd --year 2026
npm run process-sources -- --geo wd
```

| Script | Options |
| ------ | ------- |
| process-sources | `--geo`, `--year` (passed on to the steps that support them), `--no-archive` |
| download-files | `--geo`, `--year`, `--force` (download again), `--source geoportal` (skip the archive) |
| archive-files | `--geo`, `--year`, `--lookups` (include the lookups), `--prune` (remove files and releases the config no longer names), `--dry-run` |
| make-lists | `--geo`, `--year` |
| get-best-fits, make-geos, make-cm-geos | `--geo` only, because their outputs combine every year of a geography. `make-geos --clean` deletes the selected types' files first. |
| make-vtiles | `--geo`, `--year` (tileset keys from `vtiles-config.js`), `--force` (remake) |
| get-metadata, get-relations, make-search-tiles | None: these always process every geography, because the master lookup and search tiles need them all. |

Add `--help` to any of these to see its options.

### Tests

```bash
npm test
```

The tests (in `/test`) cover the shared functions in `/scripts/lib` and the consistency of the config files. They don't need the input data or network access.

## Stage 1: checking the source files

The Geoportal sometimes retires datasets or re-publishes them under new names (eg. with a `_V2` suffix), which breaks the downloads. Run:

```bash
npm run check-sources
```

This checks every dataset in `/config/source-files.js` against the Geoportal, suggests replacements for any that are missing or out of date, and lists newer releases as entries ready to paste into the config. Boundaries and codes change at most once a year, so each calendar year should use the most recent release published in it: the script suggests one release per year, covering both new years and later releases within years already in the config (eg. December rather than May). A new year is only worth adding if areas have actually changed: new codes (eg. mergers or boundary changes) or new names (renamed areas keep their code). So the script compares each new release's area codes and names with the latest year in the master lookup, without downloading any boundaries. New years with the same codes and names are listed as skipped. Suggestions are checked to have the expected fields, but always review them before using them.

## Stage 2: processing the source files (`npm run process-sources`)

### download-files

This script will download and transform boundary and lookup files from the ONS Open Geography Portal, as well as MSOA Names from the House of Commons Library. Lookups (the census lookup, the National Statistics Postcode Lookup and the MSOA names) are saved to `/input/sources`, and only their current version is kept: `npm run check-sources` reports new NSPL editions, and the MSOA names are checked for changes on every run. The census lookup (Output Area → LSOA → MSOA → local authority 2022) also gets each authority's 2022 region, joined from a separate local authority → region lookup when it's downloaded. That lookup only covers England, so Welsh authorities are given Wales (W92000004). The config can be found at `/config/source-files.js`.

Files are downloaded from the [source file archive](docs/Source-file-archive.md) (GitHub releases in [ONSdigital/geo-source-files](https://github.com/ONSdigital/geo-source-files/releases)) when it has them, so that everyone uses the same files even after the Geoportal retires a dataset; other files come from the Geoportal. Add `--source geoportal` to skip the archive. New or corrected files are added to the archive with `npm run archive-files` (see the [archive docs](docs/Source-file-archive.md)).

Boundaries are downloaded from the Geoportal as single pre-built files, which is much faster than paging through its API (the API is used if that fails). Files that have already been downloaded are skipped. Failed requests are retried. If a file can't be downloaded, the script carries on with the others, lists the failures at the end, and exits with an error; no partial files are left behind. If a dataset is reported as unavailable, run `npm run check-sources` to find its replacement.

### archive-files

This script uploads new or changed source files to the [source file archive](docs/Source-file-archive.md), so that they stay available to everyone after the Geoportal retires them. It needs the [GitHub CLI](https://cli.github.com/) logged in with write access to the archive repository; without it, `process-sources` skips this step with a warning.

### make-virtual-boundaries

The United Kingdom (K02000001), Great Britain (K03000001) and England and Wales (K04000001) have no published boundary files. This script makes them by merging their countries' boundaries, for every year and detail level of the country files. These "virtual" geographies are defined in `/config/geo-config.js`.

The UK is part of the hierarchy, as the parent of the four countries. Great Britain and England and Wales have the UK as their parent and their countries as children in their own area files, but aren't otherwise part of the hierarchy: no other area has them as a parent, and they have no parent in the master lookup.

### get-metadata

This script generates a lookup file at `/input/lookups/lookup_metadata.csv` containing area codes and names extracted from the downloaded geographic boundary files. It also adds unofficial names from the MSOA names CSV file, and calculates start and end dates for new and terminated geographies.

### get-relations

This script derives parent geographies and successor geographies (for terminated areas) based on a point-in-polygon method. Calculating these relations "on the fly" avoids the need to download and maintain a large number of official lookup files. The output from this script is merged with the metadata generated in the previous step, and outputs the [master lookup](docs/Master-lookup.md) file `/input/lookups/lookup.csv`.

### get-best-fits

This script calculates accurate best-fit lookups for every geography based on Output Area, LSOA and MSOA populated-weighted centroids. These lookups are required for the **Build a Custom Area Profile** tool.

## Stage 3: making the outputs

These scripts each depend only on the source files processed in stage 2, so run whichever you need, in any order or in parallel. The only dependencies between them are follow-on steps: `make-cm-geos` and `check-centroids` use the output of `make-geos`, `zip-vtiles` packages the vector tiles, and `make-oa-vtiles` needs `make-oa-vtiles-lookups` first.

### make-lists

This script generates [CSV lists of codes and names](docs/Area-lists.md) for places that can be found via search in **Build a Custom Area Profile** and **Explore Local Statistics**. The metadata is extracted from the lookup file generated by the `get-relations` script.

### make-geos

This script generates the [area metadata files](docs/Area-metadata-files.md) shared by **Build a Custom Area Profile** and **Explore Local Statistics** (in the `/output/geos` folder). The config can be found at `/config/geo-config.js`. Each file's child areas are grouped as in Explore Local Statistics, with the area's highest child authorities in one group (`scripts/lib/children.js`).

Existing files are overwritten. To also remove files for areas that are no longer in the lookup, add `--clean` (eg. `npm run make-geos -- --geo wd --clean`).

*Note: The .json output files in the output folder are actually gzipped to reduce file size, so cannot be opened directly. If you want to inspect their contents, you need to add .gz to their filename, and then uncompress them.*

### make-cm-geos

This optional script can be run to generate [area metadata files](docs/Area-metadata-files.md#census-map-legacy-format) for [Census maps](https://www.ons.gov.uk/census/maps/). It relies on the output of the `make-geos` script.

### make-vtiles

This script generates [vector tiles](docs/Vector-tiles.md) for the most commonly used smaller geography types, including local authorities, wards and statistical geographies. The output is in the form of .mbtiles files, written to the `/output/vtiles` folder. The config can be found at `/config/vtiles-config.js`. ([Example output](https://stevage.github.io/vector-inspector/#?url=https://cdn.ons.gov.uk/maptiles/administrative/2023/authorities-all/v1/boundaries/8/127/83.pbf&loc=9/51.504/-0.1119)).

The vector tiles can be previewed by installing [tileserver-gl-light](https://www.npmjs.com/package/tileserver-gl-light) and running the following command for the specific file you want to preview:

```bash
tileserver-gl-light ./output/vtiles/{file}.mbtiles
```

### make-oa-vtiles-lookups & make-oa-vtiles

These two scripts are used in sequence to generate [vector tiles](docs/Vector-tiles.md) for output areas suitable for both high and low zoom levels, specifically designed for use in the original version of **Build a Custom Area Profile**. ([Example output](https://stevage.github.io/vector-inspector/#?url=https://cdn.ons.gov.uk/maptiles/administrative/2021/oa/v3/boundaries/8/127/83.pbf&loc=9/51.504/-0.1119)).

Whereas Tippecanoe is capable of merging together small areas to reduce the file size of tiles at lower zoom levels, these scripts explicitly merge the smallest OAs into their LSOA and MSOA parents, which is preferable both visually and in terms of the functionality of the above product.

*Note: These tiles can also be used for standard map visualisations in the same way as the other vector tiles generated by the make-vtiles script.*

### zip-vtiles

This script unpacks the `.mbtiles` files in the **./output/vtiles** into a directory structure using Tippecanoe's **tile-join** command, and then zips the directories into the same output folder.

These ZIP files can be unzipped and uploaded to a static file service such as AWS S3, avoiding the need to run a tile server. (This is how vector tiles are currently served for ONS products.) See [Deploying to S3](docs/Deploying-to-S3.md).

### make-postcodes

This script takes the [National Statistic Postcode Lookup](https://www.ons.gov.uk/methodology/geography/geographicalproducts/postcodeproducts) as an input and generates a series of [postcode lookup files](docs/Postcode-lookup-files.md) with filenames in the form **/P.json**, **/PO.json**, **/PO1.json**, **/PO14.json**. The files contain postcodes with those prefixes and their longitude/latitude centroid coordinates. It reads the NSPL from `/input/sources/nspl.csv.gz`, which `download-files` keeps up to date with the current edition.

### make-search-tiles

This script generates a directory of [tiled GeoJSON files](docs/GeoJSON-tiles.md) that can be used for point-in-polygon "reverse geocoding" lookup to find areas that match given longitude/latitude coordinates. The tiles are generated at zoom level 12 only, and the directory structure follows an **{x}/{y}.json** pattern, equivalent to [web map tile coordinates](https://en.wikipedia.org/wiki/Tiled_web_map#Defining_a_tiled_web_map).

## Config files

All of the config files for these scripts can be found within the `/config` folder. The files that need to be updated with each geography update are:

- **source-files.js** - Defines the files to download from the ONS Geoportal, with one entry per geography and year listing the dataset for each detail level. **This is the only place years are set**: each geography covers the years it has entries for here.
- **geo-config.js** - Defines the geography types and their hierarchy. Geographies must be listed in hierarchy order (parents before children).
- **vtiles-config.js** - Defines the vector tilesets. A version of each tileset is made for every year that any of its geographies has boundaries for, named after that year (eg. `la25` combines the latest local authority, county and combined authority boundaries up to 2025).

In addition, **paths.js** defines where every input, intermediate and output file is written.

To generate partial outputs, use the `--geo` and `--year` options (see above) rather than commenting out lines in the config files.

## Updating the config files

It should be possible to add additional geographies or years by modifying the config files, without the need to edit the script files. To add a newly published year of a geography:

1. Run `npm run check-sources` and copy the suggested entry for the new year into `/config/source-files.js`. (For a later release within a year already in the config, replace that year's entry instead, and re-download it with `--force`.)
2. That's the only config change needed: the geography and its tilesets pick up the new year from `/config/source-files.js`.
3. Run `npm test` to check the config is consistent.
4. Run `npm run process-sources -- --geo {key}` to download, archive and process the new files, then make the outputs you need (stage 3), including `npm run make-lists`.

## Editing the scripts

If you *do* need to edit the processing scripts, either to fix bugs or add features, you can find these in the `/scripts` folder. Shared functions are in `/scripts/utils.js` and `/scripts/lib`, which is covered by the tests in `/test`.

See [Deploying to S3](docs/Deploying-to-S3.md) for the commands to upload the outputs with the right headers.

## Future additions

There are a number of features that could be added to these scripts in future. These include:

- Generating the raster mask map tiles used in small area mapping products (such as Census maps).
- Calculating neighbours and related geographies based on boundary files.
- Adding various additional metadata to the geo files, including codes to allow linkages to other products and API data sources.
